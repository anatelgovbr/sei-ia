# Upgrade do Servidor SEI IA 1.2.x para 1.3.0

uma instalação nova, siga o [manual de instalação](../INSTALL.md).

## 1. Versões de destino

| Componente | Versão |
|---|---:|
| SEI | 5.0.4.22 |
| Módulo SEI IA | 1.5.0 |
| Servidor de Soluções de IA | 1.3.0 |

O migrador preserva os volumes, credenciais compatíveis e o certificado da 1.2.x.
Ele não faz dump/restore: a 1.3.0 continua usando a mesma raiz definida por
`VOL_SEIIA_DIR`.

Antes da janela, execute o backup consistente definido pela política do órgão para
PostgreSQL/pgvector, metadados do Airflow, Solr e configurações privadas. Esse backup
é uma proteção operacional independente; não deve ser confundido com o diretório
criado pelo preparador, que contém somente os artefatos necessários ao de/para.

Não execute `docker compose down -v`, `make down-volumes` nem remova diretórios sob
`VOL_SEIIA_DIR` durante o upgrade.

## 2. Verifique a instalação 1.2.x

Antes da janela de manutenção:

1. confirme que a stack 1.2.x está funcionando;
2. entre no SEI, abra o Assistente, envie `Oi` e confirme a resposta;
3. confirme que o checkout não possui alterações locais desconhecidas;
4. preserve os usuários e senhas já utilizados por PostgreSQL, RabbitMQ, Solr e
   Airflow;
5. confirme os utilitários do sistema necessários ao upgrade e à stack 1.3:

```bash
# Debian / Ubuntu:
sudo apt-get update && sudo apt-get install -y make python3

# RHEL / Rocky Linux / AlmaLinux / Fedora:
sudo dnf install -y make python3

make --version
python3 --version
```
Exemplo para uma instalação em `/opt/sei-ia`:

```bash
cd /opt/sei-ia
git status --short
git describe --tags --always
```

Interrompa o procedimento se o status mostrar alterações que não foram identificadas.

## 3. Preserve a configuração 1.2.x

Execute o preparador antes de trocar a versão do checkout. Ele salva no backup os
arquivos da estrutura 1.2.x exigidos pelo migrador.

Na 1.2.x, o deploy remove o `.env` da raiz após a inicialização. O preparador
reconstrói esse arquivo somente dentro do backup, usando `env_files/default.env`,
`env_files/prod.env` e `env_files/security.env`. Não é necessário recriar o `.env`
na instalação antiga.

Execute o comando completo abaixo antes de alternar as tags:

```bash
cd /opt/sei-ia
wget --https-only -O /tmp/prepare-upgrade-1.3.sh \
  https://raw.githubusercontent.com/anatelgovbr/sei-ia/v1.3.0/migracao/1.2_1.3/prepare-upgrade-1.3.sh &&
  head -n 1 /tmp/prepare-upgrade-1.3.sh | grep -Fqx '#!/usr/bin/env bash' &&
  chmod 700 /tmp/prepare-upgrade-1.3.sh &&
  /tmp/prepare-upgrade-1.3.sh \
    --source-dir /opt/sei-ia \
    --backup-dir /opt/sei-ia/.runtime/upgrade-backup-1.2
```

O comando deve terminar com:

```text
STATUS=prepared
```

O diretório `/opt/sei-ia/.runtime/upgrade-backup-1.2` contém somente a
configuração, os Compose antigos e o material TLS necessários para a migração.
Bancos e volumes não são copiados. A pasta `.runtime` não é versionada e
permanece no local ao trocar a tag. O preparador recusa substituir um backup
existente.

## 4. Preencha as decisões novas da 1.3.0

Edite o arquivo privado criado pelo preparador:

```bash
chmod 600 /opt/sei-ia/.runtime/upgrade-backup-1.2/migration-overrides.env
vi /opt/sei-ia/.runtime/upgrade-backup-1.2/migration-overrides.env
```

Confira as variáveis abaixo e preencha as marcadas como obrigatórias:

| Variável | Finalidade | Fonte | Obrigatoriedade | Exemplo sanitizado |
|---|---|---|---|---|
| `LITELLM_PROXY_API_KEY` | Chave apresentada por Assistente, ETL e checker ao proxy local | Automática na migração (preservada da 1.2 ou gerada) | Automática (não exige preenchimento manual) | `sk-<64_HEXADECIMAIS>` |
| `LITELLM_NANO_MODEL` | Modelo físico do alias `nano` (com prefixo do provedor) | Nome ou deployment fornecido pelo administrador/provedor | Obrigatória | `openai/gpt-4o-mini` ou `azure/meu-nano` |
| `LITELLM_NANO_API_BASE` | Endereço do provedor do modelo Nano | Endpoint fornecido pelo administrador/provedor | Obrigatória | `https://api.openai.com/v1` ou `https://meu-recurso.openai.azure.com/` |
| `LITELLM_NANO_API_KEY` | Credencial do provedor do modelo Nano | Credencial exclusiva fornecida pelo administrador/provedor | Obrigatória | `<CHAVE_PROVEDOR_NANO>` |
| `LITELLM_NANO_API_VERSION` | Versão da API do modelo Nano | Documentação fornecida pelo provedor | Opcional (vazio só quando não exigido pelo provedor) | vazio (OpenAI-compatible) ou versão do provedor (ex.: `2024-06-01`, ilustrativo para Azure; não assumir universal) |
| `LITELLM_STT_MODEL` | Modelo físico de transcrição de áudio (com prefixo) | Nome ou deployment fornecido pelo administrador/provedor | Obrigatória | `openai/whisper-1` ou `azure/meu-whisper` |
| `LITELLM_STT_API_BASE` | Endereço do provedor de transcrição | Endpoint fornecido pelo administrador/provedor | Obrigatória | `https://api.openai.com/v1` ou `https://meu-recurso.openai.azure.com/` |
| `LITELLM_STT_API_KEY` | Credencial do provedor de transcrição | Credencial exclusiva fornecida pelo administrador/provedor | Obrigatória | `<CHAVE_PROVEDOR_STT>` |
| `LITELLM_STT_API_VERSION` | Versão da API de transcrição | Documentação fornecida pelo provedor | Opcional (vazio só quando não exigido pelo provedor) | vazio (OpenAI-compatible) ou versão do provedor (ex.: `2024-06-01`, ilustrativo para Azure) |
| `SEIIA_GATEWAY_HOST` | DNS/FQDN do gateway para acesso do SEI (sem protocolo/porta/path) | DNS do órgão (deve resolver a partir do SEI e constar no SAN) | Obrigatória | `seiia.dev.orgao.gov.br` (dev) ou `seiia.orgao.gov.br` (prod) |
| `SEIIA_CERT_DNS` | Nomes DNS adicionais do certificado no SAN, separados por vírgula | PKI ou DNS do órgão | Opcional | vazio ou `seiia-alt.orgao.gov.br` |
| `SEARXNG_SECRET_KEY` | Chave secreta de sessão do serviço SearXNG | Automática no preparador e migração | Automática (não vazio em runtime) | `<64_HEXADECIMAIS>` |

Para detalhes adicionais de cada parâmetro e configuração por provedor, consulte o [Manual de Instalação (seção 2.4)](../INSTALL.md#24-configurar-o-securityenv).

### Autenticação do LiteLLM

Há duas conexões, com chaves diferentes:

- **Assistente, ETL e checker → proxy LiteLLM local:** usam
  `LITELLM_PROXY_API_KEY` para autenticar as chamadas ao proxy. A migração
  preserva a chave existente ou gera uma quando ausente/vazia; não é necessário
  preenchê-la manualmente.
- **Proxy LiteLLM → provedores de modelos:** usa a `LITELLM_<TIER>_API_KEY`
  configurada para cada tier (`STANDARD`, `MINI`, `NANO`, `EMBEDDING` e `STT`).
  `LITELLM_<TIER>_API_BASE` define o endpoint e `LITELLM_<TIER>_API_VERSION`
  define a versão da API, quando exigida pelo provedor.

### Escolha dos modelos na migração

Na 1.3.0, os antigos aliases `standard` e `think` passam a usar um único modelo
Standard. O modelo `mini` mantém sua configuração separada.

- Se `standard` e `think` usavam o mesmo modelo, o migrador aproveita a
  configuração de `standard`; não é necessário escolher.
- Se usavam modelos diferentes, escolha qual será usado **antes de executar
  `--check`**. Edite `migration-overrides.env` no backup e defina
  `LITELLM_STANDARD_MODEL` com o nome físico do modelo (o valor do campo `model`
  na configuração antiga, não o alias `standard` ou `think`).
- Ao escolher um desses dois modelos, o migrador copia o endpoint, a chave e a
  versão da API do provedor correspondente.
- Para usar outro modelo, informe também `LITELLM_STANDARD_API_BASE`,
  `LITELLM_STANDARD_API_KEY` e `LITELLM_STANDARD_API_VERSION` (esta última
  pode ficar vazia quando o provedor não exigir versão).

O preflight não apresenta um menu nem pede respostas no terminal. Se a escolha
necessária não estiver no arquivo, ele termina com erro sem parar a stack.
Nesse caso, edite o arquivo e execute `--check` novamente.

Não transfira o alias `think` nem `LITELLM_THINK_MAX_TOKENS` para a configuração nova.

### Busca web com SearXNG

A 1.3.0 usa SearXNG para busca web, em substituição ao Azure AI/Bing Grounding.
Não transfira as configurações legadas desses serviços.

`SEARXNG_SECRET_KEY` é a chave de sessão do SearXNG. O preparador e o migrador
preservam a chave existente ou geram uma quando ausente/vazia; não é necessário
preenchê-la manualmente.

### DNS e certificado do gateway

O certificado preservado deve:

- Estar válido e corresponder à chave privada.
- Conter o DNS informado em `SEIIA_GATEWAY_HOST` no SAN (lista de nomes DNS
  do certificado). Apenas o CN não é suficiente.

Se o certificado não atender a esses requisitos, substitua o par de certificado
e chave em `/opt/sei-ia/.runtime/upgrade-backup-1.2/certificado` antes de continuar.
A chave privada pode usar modo `0600` ou `0640`; no modo `0640`, restrinja o grupo
aos administradores ou ao serviço responsável.

## 5. Selecione a versão 1.3.0

Atualize as tags e selecione explicitamente a versão de destino:

```bash
cd /opt/sei-ia
git fetch --tags --prune
git switch --detach v1.3.0
git describe --tags --exact-match
```

O último comando deve imprimir `v1.3.0`. Não copie os arquivos privados da 1.2.x
para a raiz nova; o migrador fará o de/para.

## 6. Execute o preflight

Com a stack 1.2.x ainda em execução:

```bash
cd /opt/sei-ia
bash migracao/1.2_1.3/deploy-migracao-1.2-1.3.sh \
  --from-backup /opt/sei-ia/.runtime/upgrade-backup-1.2 \
  --check
```

O `--check` não para serviços nem escreve no destino. Só prossiga quando a saída
terminar com:

```text
MIGRATION_STATUS=ready
```

Corrija qualquer variável, conflito de modelo, permissão ou certificado informado
pelo preflight e execute o mesmo comando novamente.

## 7. Atualize o SEI e o Módulo SEI IA

Na janela de manutenção, atualize o SEI para `5.0.4.22` e o Módulo SEI IA para
`1.5.0` conforme os respectivos pacotes oficiais. Compare antes as versões do código
e das bases; não execute novamente um atualizador quando ambos já estiverem na versão
de destino.

Quando houver atualização pendente:

1. execute primeiro o atualizador do módulo no SIP;
2. execute depois o atualizador do módulo no SEI;
3. exija `FIM`, sem erros, nos dois comandos;
4. confirme a versão `1.5.0` nas bases do SIP e do SEI;
5. encerre as sessões abertas e entre novamente no SEI.

Use o README do Módulo SEI IA como fonte de verdade para os comandos e parâmetros
dessa atualização. Não altere manualmente as URLs individuais das operações.

## 8. Aplique a migração do servidor

Execute o mesmo comando do preflight, agora com `--apply`:

```bash
cd /opt/sei-ia
bash migracao/1.2_1.3/deploy-migracao-1.2-1.3.sh \
  --from-backup /opt/sei-ia/.runtime/upgrade-backup-1.2 \
  --apply
```

O comando:

1. repete o preflight;
2. para somente a composição 1.2.x, sem remover volumes;
3. gera `security.env` e `litellm_config.yaml` no contrato 1.3.0;
4. preserva o certificado validado em `.runtime/certs`;
5. executa `make up` e `make check`.

O `litellm_config.yaml` gerado publica os aliases `standard`, `mini`, `nano`,
`embedding` e `speech-to-text`. Os modelos físicos e as credenciais ficam no
`security.env`.

As configurações preservadas incluem:

- `LITELLM_EMBEDDING_MODEL`: mantém o modelo físico usado pelo alias `embedding`
  da 1.2.x. Não substitua esse valor pelo nome do alias.
- `LOG_LEVEL`: mantém o nível de log declarado na origem.

Não execute `make up` ou `make check` separadamente. A migração termina somente com:

```text
[migracao 1.2->1.3] Migração concluída com todos os gates aprovados.
```

Se o comando for interrompido depois de gravar a configuração, execute o mesmo
`--apply` novamente. O migrador retoma a subida e o checker. Depois da conclusão,
uma nova execução informa `already-migrated` e não reinicia a stack.

## 9. Confirme TLS e as integrações

Em cada nó PHP do SEI, disponibilize a CA confiável em:

```text
/opt/sei/config/mod-ia/seiia.cert.pem
```

Para certificado autoassinado, use o PEM público preservado pelo migrador. Para
certificado institucional, use a CA bundle aprovada pelo órgão. Nunca copie a chave
privada para o SEI e não desabilite a validação TLS.

No SEI, configure nas duas integrações do módulo a mesma URL base:

```text
https://<SEIIA_GATEWAY_HOST>
```

Não inclua porta, barra final ou caminho. Use a ação de validação da própria tela e
mantenha os registros ativos.

## 10. Valide o resultado

Confirme que o `make check`, executado pelo migrador, terminou sem erros. Depois:

1. saia e entre novamente no SEI;
2. abra o Assistente com um usuário autorizado;
3. envie `Oi`;
4. confirme que uma resposta é exibida normalmente.

Essa validação pela interface é obrigatória; o healthcheck isolado não comprova a
integração completa.

## 11. Conflitos comuns

| Sintoma | Causa provável | Correção |
|---|---|---|
| O preparador informa arquivo ausente | A instalação 1.2.x não conserva a estrutura publicada | Restaure o arquivo da mesma tag 1.2.x antes de criar o backup. |
| O preflight informa conflito entre modelos `standard` e `think` | Os modelos eram diferentes e a escolha para a 1.3.0 não foi registrada | Edite `migration-overrides.env` no backup, preencha `LITELLM_STANDARD_MODEL` com o nome físico do modelo escolhido e execute `--check` novamente. Não há seleção interativa. |
| O preflight rejeita o certificado | Certificado vencido, chave divergente, permissão aberta ou DNS ausente no SAN | Instale um par válido no backup e repita `--check`. |
| `make up` falha em RabbitMQ, PostgreSQL, Solr ou Airflow | Credencial preservada não corresponde ao volume ou serviço ainda não ficou saudável | Corrija a primeira falha indicada nos logs e repita `--apply`. |
| `make check` acusa variável ausente, extra ou duplicada | Um arquivo gerado foi alterado fora do contrato | Remova a alteração manual e repita o migrador com os mesmos artefatos. |
| A validação TLS falha no SEI | DNS, SAN, cadeia ou CA bundle estão incorretos no nó PHP | Corrija a confiança no SEI; não use modo inseguro. |
| O Assistente não aparece após atualizar o módulo | A sessão ainda mantém recursos e permissões antigos | Encerre a sessão e autentique novamente. |
