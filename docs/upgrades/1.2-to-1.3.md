# Upgrade do Servidor SEI IA 1.2.x para 1.3

Use este procedimento somente para atualizar uma instalação 1.2.x existente. Para
uma instalação nova, siga o [manual de instalação](../INSTALL.md).

## 1. Versões de destino

| Componente | Versão |
|---|---:|
| SEI | 5.0.4.22 |
| Módulo SEI IA | 1.5.0 |
| Servidor de Soluções de IA | 1.3 |

O migrador preserva os volumes, credenciais compatíveis e o certificado da 1.2.x.
Ele não faz dump/restore: a 1.3 continua usando a mesma raiz definida por
`VOL_SEIIA_DIR`.

Antes da janela, execute o backup consistente definido pela política do órgão para
PostgreSQL/pgvector, metadados do Airflow, Solr e configurações privadas. Esse backup
é uma proteção operacional independente; não deve ser confundido com o diretório
criado pelo preparador, que contém somente os artefatos necessários ao de/para.

Não execute `docker compose down -v`, `make down-volumes` nem remova diretórios sob
`VOL_SEIIA_DIR` durante o upgrade.

## 2. Verifique a instalação 1.2.x

Antes da janela de manutenção:

1. confirme que a stack 1.2.x está funcionando;
2. entre no SEI, abra o Assistente, envie `Oi` e confirme a resposta;
3. confirme que o checkout não possui alterações locais desconhecidas;
4. preserve os usuários e senhas já utilizados por PostgreSQL, RabbitMQ, Solr e
   Airflow.

Exemplo para uma instalação em `/opt/sei-ia`:

```bash
cd /opt/sei-ia
git status --short
git describe --tags --always
```

Interrompa o procedimento se o status mostrar alterações que não foram identificadas.

## 3. Preserve a configuração 1.2.x

O preparador precisa ser executado antes de trocar a versão do checkout, pois ele
salva os arquivos da estrutura 1.2.x exigidos pelo migrador.

```bash
cd /opt/sei-ia
wget --https-only -O /tmp/prepare-upgrade-1.3.sh \
  https://raw.githubusercontent.com/anatelgovbr/sei-ia/v1.3.0/migracao/1.2_1.3/prepare-upgrade-1.3.sh &&
  head -n 1 /tmp/prepare-upgrade-1.3.sh | grep -Fqx '#!/usr/bin/env bash' &&
  chmod 700 /tmp/prepare-upgrade-1.3.sh &&
  /tmp/prepare-upgrade-1.3.sh \
    --source-dir /opt/sei-ia \
    --backup-dir /opt/sei-ia/.runtime/upgrade-backup-1.2
```

O comando deve terminar com:

```text
STATUS=prepared
```

O diretório `/opt/sei-ia/.runtime/upgrade-backup-1.2` contém somente a
configuração, os Compose antigos e o material TLS necessários para a migração.
Bancos e volumes não são copiados. A pasta `.runtime` não é versionada e
permanece no local ao trocar a tag. O preparador recusa substituir um backup
existente.

## 4. Preencha as decisões novas da 1.3

Edite o arquivo privado criado pelo preparador:

```bash
chmod 600 /opt/sei-ia/.runtime/upgrade-backup-1.2/migration-overrides.env
vi /opt/sei-ia/.runtime/upgrade-backup-1.2/migration-overrides.env
```

Preencha os valores abaixo:

| Variável | Finalidade |
|---|---|
| `LITELLM_NANO_MODEL` | modelo usado pelo alias `nano` |
| `LITELLM_NANO_API_BASE` | endereço do provedor do modelo Nano |
| `LITELLM_NANO_API_KEY` | credencial do provedor do modelo Nano |
| `LITELLM_NANO_API_VERSION` | versão da API do modelo Nano, ou vazio quando o provedor não utiliza esse parâmetro |
| `LITELLM_STT_MODEL` | modelo de transcrição |
| `LITELLM_STT_API_BASE` | endereço do provedor de transcrição |
| `LITELLM_STT_API_KEY` | credencial do provedor de transcrição |
| `LITELLM_STT_API_VERSION` | versão da API, ou vazio quando o provedor não utiliza esse parâmetro |
| `SEIIA_GATEWAY_HOST` | DNS/FQDN usado pelo SEI para acessar o gateway, sem protocolo, porta ou caminho |
| `SEIIA_CERT_DNS` | nomes DNS adicionais do certificado, separados por vírgula, ou vazio |

O migrador transfere separadamente o provedor do alias `standard` para as variáveis
Standard e o provedor do alias `mini` para as variáveis Mini. Se os modelos antigos
`standard` e `think` forem diferentes, o preflight solicitará
`LITELLM_STANDARD_MODEL`. Quando a escolha não corresponder exatamente a um desses
aliases, informe também `LITELLM_STANDARD_API_BASE`, `LITELLM_STANDARD_API_KEY` e
`LITELLM_STANDARD_API_VERSION`.

`SEARXNG_SECRET_KEY` já é gerada pelo preparador. Não transfira as configurações
legadas de Azure AI/Bing Grounding, aliases `think` ou
`LITELLM_THINK_MAX_TOKENS`: a 1.3 usa SearXNG e o modelo consolidado do Assistente.

O certificado preservado precisa estar válido, corresponder à chave privada e
conter `SEIIA_GATEWAY_HOST` no SAN. Se o certificado antigo contiver apenas CN,
substitua o par em
`/opt/sei-ia/.runtime/upgrade-backup-1.2/certificado` por um certificado
adequado antes de continuar. A chave pode usar modo `0600` ou `0640`; no modo
`0640`, o grupo deve ser restrito aos administradores ou ao serviço responsável.

## 5. Selecione a versão 1.3

Atualize as tags e selecione explicitamente a versão de destino:

```bash
cd /opt/sei-ia
git fetch --tags --prune
git switch --detach v1.3.0
git describe --tags --exact-match
```

O último comando deve imprimir `v1.3.0`. Não copie os arquivos privados da 1.2.x
para a raiz nova; o migrador fará o de/para.

## 6. Execute o preflight

Com a stack 1.2.x ainda em execução:

```bash
cd /opt/sei-ia
bash migracao/1.2_1.3/deploy-migracao-1.2-1.3.sh \
  --from-backup /opt/sei-ia/.runtime/upgrade-backup-1.2 \
  --check
```

O `--check` não para serviços nem escreve no destino. Só prossiga quando a saída
terminar com:

```text
MIGRATION_STATUS=ready
```

Corrija qualquer variável, conflito de modelo, permissão ou certificado informado
pelo preflight e execute o mesmo comando novamente.

## 7. Atualize o SEI e o Módulo SEI IA

Na janela de manutenção, atualize o SEI para `5.0.4.22` e o Módulo SEI IA para
`1.5.0` conforme os respectivos pacotes oficiais. Compare antes as versões do código
e das bases; não execute novamente um atualizador quando ambos já estiverem na versão
de destino.

Quando houver atualização pendente:

1. execute primeiro o atualizador do módulo no SIP;
2. execute depois o atualizador do módulo no SEI;
3. exija `FIM`, sem erros, nos dois comandos;
4. confirme a versão `1.5.0` nas bases do SIP e do SEI;
5. encerre as sessões abertas e entre novamente no SEI.

Use o README do Módulo SEI IA como fonte de verdade para os comandos e parâmetros
dessa atualização. Não altere manualmente as URLs individuais das operações.

## 8. Aplique a migração do servidor

Execute o mesmo comando do preflight, agora com `--apply`:

```bash
cd /opt/sei-ia
bash migracao/1.2_1.3/deploy-migracao-1.2-1.3.sh \
  --from-backup /opt/sei-ia/.runtime/upgrade-backup-1.2 \
  --apply
```

O comando:

1. repete o preflight;
2. para somente a composição 1.2.x, sem remover volumes;
3. gera `security.env` e `litellm_config.yaml` no contrato 1.3;
4. preserva o certificado validado em `.runtime/certs`;
5. executa `make up` e `make check`.

O `litellm_config.yaml` gerado publica os aliases `standard`, `mini`, `nano`,
`embedding` e `speech-to-text`. Os modelos e as credenciais ficam no `security.env`.
O migrador mantém em `LITELLM_EMBEDDING_MODEL` o modelo usado pela entrada
`embedding` da 1.2.x; esse valor não deve ser substituído pelo nome do alias.

Não execute `make up` ou `make check` separadamente. A migração termina somente com:

```text
[migracao 1.2->1.3] Migração concluída com todos os gates aprovados.
```

Se o comando for interrompido depois de gravar a configuração, execute o mesmo
`--apply` novamente. O migrador retoma a subida e o checker. Depois da conclusão,
uma nova execução informa `already-migrated` e não reinicia a stack.

## 9. Confirme TLS e as integrações

Em cada nó PHP do SEI, disponibilize a CA confiável em:

```text
/opt/sei/config/mod-ia/seiia.cert.pem
```

Para certificado autoassinado, use o PEM público preservado pelo migrador. Para
certificado institucional, use a CA bundle aprovada pelo órgão. Nunca copie a chave
privada para o SEI e não desabilite a validação TLS.

No SEI, configure nas duas integrações do módulo a mesma URL base:

```text
https://<SEIIA_GATEWAY_HOST>
```

Não inclua porta, barra final ou caminho. Use a ação de validação da própria tela e
mantenha os registros ativos.

## 10. Valide o resultado

Confirme que o `make check`, executado pelo migrador, terminou sem erros. Depois:

1. saia e entre novamente no SEI;
2. abra o Assistente com um usuário autorizado;
3. envie `Oi`;
4. confirme que uma resposta é exibida normalmente.

Essa validação pela interface é obrigatória; o healthcheck isolado não comprova a
integração completa.

## 11. Conflitos comuns

| Sintoma | Causa provável | Correção |
|---|---|---|
| O preparador informa arquivo ausente | A instalação 1.2.x não conserva a estrutura publicada | Restaure o arquivo da mesma tag 1.2.x antes de criar o backup. |
| O preflight informa conflito entre modelos | A 1.2.x usava endpoints ou credenciais incompatíveis entre aliases | Registre no `migration-overrides.env` a decisão consolidada solicitada pela mensagem. |
| O preflight rejeita o certificado | Certificado vencido, chave divergente, permissão aberta ou DNS ausente no SAN | Instale um par válido no backup e repita `--check`. |
| `make up` falha em RabbitMQ, PostgreSQL, Solr ou Airflow | Credencial preservada não corresponde ao volume ou serviço ainda não ficou saudável | Corrija a primeira falha indicada nos logs e repita `--apply`. |
| `make check` acusa variável ausente, extra ou duplicada | Um arquivo gerado foi alterado fora do contrato | Remova a alteração manual e repita o migrador com os mesmos artefatos. |
| A validação TLS falha no SEI | DNS, SAN, cadeia ou CA bundle estão incorretos no nó PHP | Corrija a confiança no SEI; não use modo inseguro. |
| O Assistente não aparece após atualizar o módulo | A sessão ainda mantém recursos e permissões antigos | Encerre a sessão e autentique novamente. |
